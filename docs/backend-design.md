# Архитектура и развитие поиска

## Текущая реализация

Node.js 24, встроенный HTTP-сервер и SQLite. Интерфейс вызывает POST /api/search; сервер строит профиль запроса, применяет обязательные ограничения и сортирует весь набор совпадений до пагинации. Каталог находится вне Git. Импорт нормализует поля, проверяет географию и группирует дубли.

Профиль разделяет hard — обязательные условия, soft — пожелания и unknown — непроверяемые условия. Источник профиля сейчас — правила либо ручные фильтры. Это исходная версия для сравнения с языковой моделью, не обученный поиск.

Для пользовательской сессии сохраняются запросы, выданные объекты и события detail_open, favorite_add, favorite_remove, source_open. Сервер проверяет принадлежность события сессии и выдаче. Cookie-сессия не заменяет авторизацию. Отданная сервером карточка не равна подтверждённому просмотру; переход к источнику не равен контакту или сделке.

## Целевая интеграция LLM

1. Текст запроса и компактная схема направляются модели.
2. Сервер проверяет структуру, диапазоны, географию и противоречия ответа; неоднозначности требуют уточнения.
3. Обязательные фильтры применяются в SQL без скрытого ослабления.
4. Допустимые кандидаты ранжируются по мягким предпочтениям, затем выдаются с проверяемыми объяснениями.

Модель не генерирует произвольный SQL, не получает ключ Metrapi и весь каталог за каждый запрос. Описания объектов рассматриваются как недоверенные данные. Отсутствие характеристики не заменяется предположением.

Первый этап — независимый адаптер извлечения критериев с тайм-аутом, валидацией, явным режимом отказа и учётом usage. Смена модели должна происходить через конфигурацию. Провайдер, модель и бюджет пока не выбраны; [сравнение стоимости](llm-budget.md).

Семантическое ранжирование — отдельный этап. Векторы описаний вычисляются заранее и обновляются по изменению текста. Версии и размерности моделей не смешиваются. Обучаемый ранжировщик имеет смысл при достаточной разметке пар запрос–объект; наличие каталога само по себе разметкой не является.

## Проверка качества

Нужны отдельные наборы настройки и отложенной проверки. Измеряются точность извлечения полей, нарушения обязательных условий, качество уточнений, nDCG@10, задержка и стоимость. Дубли не должны попадать одновременно в обучение и проверку.

Пользовательское исследование сравнивает одинаковые задачи и каталог, время и успешность выполнения, число исправлений и субъективное удобство. Детали — в [плане демонстрации и исследования](mvp-review.md). Вывод о росте конверсии до эксперимента не делается.

## Развёртывание

Для локальной демонстрации достаточно Node.js и SQLite. Для публичного сервера нужны HTTPS, аутентификация, ограничение запросов, резервное копирование и политика хранения событий. PostgreSQL/pgvector рассматриваются при росте нагрузки; отдельные Redis, GPU и векторный сервис на этапе MVP не обязательны.

Обновление Metrapi должно стать отдельной фоновой задачей с сохранением cursor и учётом снятых объявлений. Текущий снимок не доказывает актуальность предложений; живой адаптер получает одну страницу кандидатов. Платные вызовы разрешаются только после согласования конфигурации и лимита.
