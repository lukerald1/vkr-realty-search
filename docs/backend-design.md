# Бэкенд и LLM: решение для ВКР

Дата проверки документации: 22.10.2026. География исследования — Санкт-Петербург как субъект РФ, включая муниципальные города в его составе, без Ленинградской области. Покупка и долгосрочная аренда квартир — отдельные режимы.

## Что реализовано в 0.2

Node.js 24 + встроенный SQLite: потоковый импорт JSONL, нормализация, контроль географии, дедупликация, SQL-фильтры и глобальная сортировка до пагинации. Каталог хранится в `data/catalog.sqlite`. Данные не попадают в Git или в статическую директорию.

В `data/activity.sqlite` сохраняются запросы и действия в поисковой сессии. Сессия задаётся HttpOnly-cookie. API истории возвращает только запросы текущей сессии; событие принимается только для объекта, выданного этой сессии. Это локальная демонстрационная изоляция, а не аккаунты и не готовая авторизация для публичного сервера.

События: `detail_open`, `favorite_add`, `favorite_remove`, `source_open`. `served_results` означает отданные сервером объекты, не подтверждённый просмотр пользователем. Переход к площадке не считается контактом, просмотром квартиры или сделкой. Тестовые действия нужно исключить из будущего эксперимента.

## Предлагаемый поток

1. Запрос пользователя + текущее состояние критериев → LLM → JSON-профиль.
2. Сервер проверяет схему, диапазоны, географию и конфликты; при неоднозначности задаёт уточнение.
3. SQL применяет жёсткие ограничения. Они не снимаются для улучшения выдачи.
4. Мягкие пожелания сопоставляются с описаниями через эмбеддинги и признаки объектов.
5. Ранжировщик сортирует допустимые варианты. На старте — объяснимые веса; после разметки — CatBoostRanker как исследовательская модель.
6. Объяснение опирается на реальные поля и фрагменты описания. «Тихо» со слов продавца не равно подтверждённому уровню шума. Отсутствующие сведения остаются неизвестными.

LLM не генерирует SQL, не получает ключ Metrapi и не читает всю базу за каждый запрос. Для разбора нужен только пользовательский текст и компактная схема. Описания объявлений — недоверенные данные, не инструкции модели.

## Выбор модели

Для первого российского API-пилота предлагается **YandexGPT Pro 5.1**, URI `gpt://<folder-id>/yandexgpt-5.1`, с JSON Schema. Модель есть в [официальном каталоге](https://aistudio.yandex.ru/ru/docs/ai-studio/concepts/generation/models); поддержка форматирования описана в [документации](https://aistudio.yandex.ru/ru/docs/ai-studio/concepts/generation/structured-output). Это выбор для проверки, а не утверждение о превосходстве на запросах недвижимости. YandexGPT Lite 5 не закладываем в новый проект: в каталоге объявлено отключение 15.11.2026.

Сравнить с **GPT-6 Luna**, если есть официальный доступ к API в поддерживаемой стране. В каталоге OpenAI это модель для недорогих узких задач со структурированными ответами; [страница модели](https://developers.openai.com/api/docs/models/gpt-6-luna). Россия отсутствует в [списке поддерживаемых стран API](https://developers.openai.com/api/docs/supported-countries), поэтому её нельзя считать гарантированно доступным вариантом для запуска из РФ. Подписка в приложении и API-доступ — разные способы подключения.

Для первого семантического поиска предлагается проверить пару **Yandex Text Embeddings v2 doc/query**: разные модели для документов и короткого запроса. [Официальное описание](https://aistudio.yandex.ru/ru/docs/ai-studio/concepts/embeddings). Векторизацию каталога выполнять один раз, потом только для изменившихся объектов. Не смешивать версии/размерности в одном индексе.

Платные модели и векторизация в текущей итерации не вызывались. Ключи, бюджет и провайдер для реального теста ещё не настроены.

## Как выбрать окончательно

Разметить 100–200 русских запросов: бюджет, отрицания, метро пешком/транспортом, районы, неопределённые предпочтения, смена и снятие условий, выход за географию. Отделить набор настройки промпта от отложенного теста.

Сравнить правила, LLM-извлечение и комбинацию LLM+ранжирование: точность полей, нарушения обязательных условий, доля корректных уточнений, nDCG@10 по оценкам людей, задержка p50/p95 и стоимость запроса. Для CatBoost нужна разметка пар запрос–объект: наличие 26 тысяч объявлений само по себе не является обучающей разметкой.

Не использовать клики как готовую релевантность: они зависят от позиции, фотографии и цены. Не допускать попадания дублей одной квартиры одновременно в обучение и тест.

## Развёртывание

Для локальной защиты достаточно SQLite и текущего Node-сервера. Для постоянной виртуальной машины: HTTPS через reverse proxy, авторизация, резервное копирование, ограничения запросов и фоновые обновления Metrapi. PostgreSQL + pgvector имеет смысл при переходе к нескольким пользователям и постоянному векторному индексу; отдельные Redis и Qdrant на старте не обязательны.

Синхронизация Metrapi — отдельная задача по расписанию с сохранением cursor, учётом снятий и лимита на общий ключ. Присланные `.cursor` относятся к старым выгрузкам: текущая итерация их не меняет и не использует как доказательство свежести. Живой API не нужен для каждого поиска по локальной базе.
